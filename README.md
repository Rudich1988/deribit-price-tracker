# Deribit Price Tracker

Сервис следит за ценами BTC и ETH на криптобирже [Deribit](https://docs.deribit.com/).

Раз в минуту он забирает с биржи текущую **index price** для `btc_usd` и `eth_usd`
и сохраняет в PostgreSQL тикер, цену и время (UNIX timestamp). Сохранённые цены
можно получить через HTTP API: все цены валюты, последнюю цену и цены за
выбранные даты.

## Как это работает

```
            каждые 60 секунд
 Celery beat ───────────────► Celery worker ──── GET /public/get_index_price ───► Deribit
                                   │
                                   ▼  сохраняет тикер, цену, время
                              PostgreSQL
                                   ▲
                                   │  читает
 Клиент ──── GET /prices?ticker=… ──► FastAPI
```

- **Celery worker** со встроенным **beat** раз в минуту запускает задачу.
  Задача параллельно запрашивает обе цены у Deribit и записывает их в базу.
- **FastAPI** отдаёт сохранённые данные. Сам на биржу он не ходит.
- **Redis** передаёт задачи от beat к worker (брокер Celery).

## Технологии

- Python 3.12, FastAPI, Pydantic
- Celery + Redis — периодический сбор цен
- aiohttp + tenacity — клиент Deribit с таймаутами и повторами
- PostgreSQL, SQLAlchemy 2 (async), asyncpg, Alembic
- pytest, ruff, Poetry, Docker Compose

## Запуск и проверка

Нужны только Docker и make. Python и Poetry ставить не нужно: тесты и
линтер тоже запускаются в Docker.

Склонируйте репозиторий и перейдите в папку проекта:

```bash
git clone <url-репозитория> deribit-price-tracker
```

```bash
cd deribit-price-tracker
```

1. Создайте файл `.env` из шаблона `.env.example`. Значений из шаблона
   достаточно, чтобы всё запустить:

```bash
make env
```

2. Соберите и запустите проект. Команда соберёт образ, применит миграции
   базы и запустит все сервисы:

```bash
make up
```

3. Подождите минуту, пока worker сохранит первые цены, и запросите
   последнюю цену BTC:

```bash
curl "http://localhost:8000/prices/latest?ticker=btc_usd"
```

Документация API (Swagger), где все методы можно вызвать прямо из браузера:
http://localhost:8000/docs

4. Запустите тесты. Они выполняются внутри контейнера `app`, вместе с
   тестами на базе данных:

```bash
make test
```

5. Запустите линтер:

```bash
make lint
```

6. Посмотрите, как worker раз в минуту забирает цены:

```bash
make logs SERVICE=worker
```

7. Остановите проект. Данные в базе сохранятся:

```bash
make down
```

Остановить проект и удалить базу вместе с данными:

```bash
make down-volumes
```

Все команды с описанием:

```bash
make help
```

Если make не установлен, проект запускается напрямую через Docker Compose:

```bash
docker compose up -d --build --wait
```

### Какие контейнеры запускаются

- `db` — PostgreSQL 17. С хоста доступен только на `127.0.0.1:5433`.
- `redis` — брокер задач для Celery.
- `migrate` — применяет миграции при запуске и сразу завершается.
- `app` — FastAPI на порту `8000`.
- `worker` — Celery worker со встроенным beat, собирает цены.

У `app`, `migrate` и `worker` общий образ, он собирается один раз.

## Примеры запросов

У всех методов обязательный query-параметр `ticker`: `btc_usd` или `eth_usd`.

### Все сохранённые цены валюты

```bash
curl "http://localhost:8000/prices?ticker=btc_usd"
```

Ответ — список, отсортированный по времени:

```json
[
  {"ticker": "btc_usd", "price": 81179.33, "timestamp": 1792053605},
  {"ticker": "btc_usd", "price": 81167.5, "timestamp": 1792053661}
]
```

Если цен ещё нет, придёт пустой список `[]`.

`timestamp` — время в формате UNIX timestamp, как требует ТЗ: число секунд,
прошедших с 1 января 1970 года (UTC). Например, `1792053661` — это
15 октября 2026 года, 08:41:01 UTC. Перевести число в
обычную дату можно в терминале:

```bash
date -u -d @1792053661
```

### Последняя цена валюты

```bash
curl "http://localhost:8000/prices/latest?ticker=eth_usd"
```

Ответ:

```json
{"ticker": "eth_usd", "price": 2371.59, "timestamp": 1792053661}
```

Если цен ещё нет, придёт `404`:

```json
{"detail": "No prices saved for eth_usd"}
```

### Цены с фильтром по дате

Дата вводится в формате `ГГГГ-ММ-ДД`: 15 октября 2026 года — это
`2026-10-15`. В Swagger даты вводятся так же. Дата в другом виде, например
`15.10.2026`, вернёт ошибку `422`.

- Обе границы включительно: `date_from=2026-10-15&date_to=2026-10-15` — это
  весь день 15 октября.
- Дни считаются по UTC: день начинается в 00:00 UTC, а не по местному
  времени.

Цены за один день:

```bash
curl "http://localhost:8000/prices/by-date?ticker=btc_usd&date_from=2026-10-15&date_to=2026-10-15"
```

Цены за период:

```bash
curl "http://localhost:8000/prices/by-date?ticker=btc_usd&date_from=2026-10-01&date_to=2026-10-31"
```

Цены начиная с даты и до сегодняшнего дня:

```bash
curl "http://localhost:8000/prices/by-date?ticker=btc_usd&date_from=2026-10-15"
```

Цены до конца указанной даты:

```bash
curl "http://localhost:8000/prices/by-date?ticker=btc_usd&date_to=2026-10-15"
```

Обе даты необязательны. Без них вернутся все цены валюты.

### Ошибки в запросе

Неизвестный тикер, неверная дата или `date_from` позже `date_to` дают
ответ `422` с описанием ошибки:

```bash
curl "http://localhost:8000/prices/latest?ticker=doge_usd"
```

```json
{"detail": [{"type": "enum", "loc": ["query", "ticker"], "msg": "Input should be 'btc_usd' or 'eth_usd'", "input": "doge_usd"}]}
```

## Настройки

Все настройки задаются переменными окружения в файле `.env`. Шаблон лежит в
`.env.example`. Секреты в коде и в Docker-файлах не хранятся.

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` — пользователь, пароль и
  имя базы для контейнера PostgreSQL.
- `DATABASE_URL` — адрес базы для приложения, например
  `postgresql+asyncpg://postgres:пароль@db:5432/prices`. В Docker хост — `db`.
- `REDIS_URL` — брокер Celery, по умолчанию `redis://redis:6379/0`.
- `DERIBIT_BASE_URL` — адрес API Deribit, по умолчанию
  `https://www.deribit.com/api/v2`.
- `FETCH_INTERVAL_SECONDS` — как часто забирать цены, по умолчанию `60`.
- `HTTP_TIMEOUT`, `HTTP_CONNECT_TIMEOUT` — таймауты запроса к Deribit и
  подключения, в секундах (по умолчанию `10` и `3`).
- `HTTP_RETRY_ATTEMPTS` — сколько раз пробовать запрос при временной
  ошибке, по умолчанию `3`.
- `LOG_LEVEL` — уровень логов, по умолчанию `INFO`.
- `DEBUG` — `true` включает вывод SQL-запросов в лог.
- `POSTGRES_HOST_PORT`, `APP_PORT` — необязательные: порты на хосте для базы
  (по умолчанию `5433`) и API (по умолчанию `8000`).

## Design decisions

Здесь описано, какие решения приняты и почему.

### Архитектура: слои по DDD

Код разделён на слои, и каждый слой делает только своё:

- **Роутер** (`routers.py`) принимает запрос, переводит pydantic-схему в
  dataclass, создаёт репозиторий и сервис, вызывает сервис и возвращает ответ.
  Бизнес-логики в нём нет.
- **Задача Celery** (`tasks.py`) — такая же тонкая точка входа, как роутер:
  собирает зависимости и вызывает один метод сервиса.
- **Сервис** (`services.py`) содержит бизнес-логику. Он ничего не знает про
  FastAPI, Pydantic, SQLAlchemy и aiohttp, а работает только через
  репозиторий и источник цен.
- **Репозиторий** (`repositories.py`) делает только запросы к базе и
  возвращает dataclass, а не объекты ORM.
- **Клиент** (`clients.py`) только ходит в API Deribit и тоже возвращает
  dataclass.

Между слоями передаются только dataclass из `dto.py`. Поэтому слои можно
тестировать отдельно и менять независимо.

Сервис сбора цен зависит не от `DeribitClient`, а от интерфейса
`PriceSource` (`Protocol`). Так сервис не привязан к конкретной бирже, а в
тестах вместо настоящего клиента подставляется простой фейк.

### Нет глобальных переменных

На уровне модулей нет ни переменных, ни констант. Там только объявления:
классы, функции, enum.

- FastAPI и Celery создаются фабриками `create_app()` и `create_celery_app()`.
- Подключение к базе создаётся при старте приложения и передаётся в
  эндпоинты через зависимость FastAPI `DatabaseDep`.
- Логгеры, пути API и коды ошибок — атрибуты классов.
- Набор тикеров — enum `Ticker`. Это тип, а не переменная, и он же
  проверяет параметр `ticker` в запросах.
- Команда `celery -A` умеет работать только с готовым объектом `Celery` в
  модуле, а это была бы глобальная переменная. Поэтому Celery запускается
  через свою точку входа:
  `python -m deribit_price_tracker.worker worker --beat`. Она создаёт
  приложение фабрикой и передаёт ему аргументы командной строки.

### Откуда берутся цены

- Используется метод `public/get_index_price`. Он публичный, ключи API не
  нужны.
- Вебхуков у Deribit нет. Данные в реальном времени есть только через
  WebSocket-подписку, но ТЗ просит забирать цену раз в минуту, поэтому
  выбран обычный HTTP-запрос по расписанию.
- Время берётся из ответа биржи: поле `usOut` — время ответа в микросекундах.
  Это точнее, чем время нашего сервера. Если поля нет, берётся текущее время.

### Цены хранятся точно

- В коде цена — `Decimal`, в базе — `Numeric(20, 8)`. Тип `float` округляет
  дробные числа, а для денег это недопустимо.
- JSON от Deribit разбирается сразу в `Decimal`, без промежуточного `float`.
- В ответе API цена отдаётся обычным JSON-числом (`81179.33`), как у
  Deribit, а не строкой `"81179.33000000"`.

### Надёжный клиент Deribit

- Базовый класс `BaseHTTPClient` отвечает за сессию, таймауты, повторы и
  ошибки. `DeribitClient` наследует его и добавляет только своё: путь метода и
  разбор ответа.
- Таймауты заданы явно. По умолчанию у aiohttp таймаут 5 минут, а это
  слишком долго.
- Повторы (tenacity) делаются только при временных ошибках: сеть, таймаут,
  ответы 429/502/503/504 и ошибка Deribit `10028` (слишком много запросов).
  Пауза между попытками растёт: 0.5 → 1 → 2 → 3 секунды. Ошибки вроде
  «неверный параметр» не повторяются: повтор их не исправит.
- Наружу не выходят исключения aiohttp, только свои: `ExternalServiceError`
  и `ExternalServiceUnavailableError`. Остальной код не зависит от aiohttp.
- **Одна HTTP-сессия на один запуск задачи**, а не на всё приложение. Каждый
  запуск задачи Celery работает в своём event loop, а сессия aiohttp
  привязана к loop. Держать вечную сессию тоже нет смысла: запросы идут раз в
  минуту, а aiohttp закрывает простаивающее соединение через 15 секунд. Внутри
  запуска оба запроса идут через одну сессию.
- Сознательно не сделаны circuit breaker, метрики и трейсинг. Для двух
  запросов в минуту к публичному методу это лишнее.

### Сбор цен

- Оба тикера запрашиваются параллельно.
- Ошибка по одному тикеру не мешает сохранить другой. Ожидаемая ошибка
  (биржа недоступна) пишется в лог одной строкой, неожиданная — с
  traceback.
- Задача Celery сама себя не повторяет: через минуту будет новый запуск.
- У задачи в расписании `expires` равен интервалу. Если worker был выключен,
  старые запуски не выполнятся пачкой при старте.

### Контейнеры: почему их больше двух

В ТЗ необязательное требование — два контейнера, для приложения и базы. Но
Celery не работает без брокера, а периодический запуск задач — это ещё один
процесс (beat). Поэтому контейнеров больше: `app`, `worker`, `redis`, `db`.
Смысл требования сохранён: приложение и база разделены.

- **Beat запущен внутри worker** (флаг `--beat`). Так проще, и для одного
  worker этого достаточно. Если запустить несколько копий worker, beat нужно
  вынести в отдельный контейнер. Иначе каждая копия будет ставить свою задачу,
  и цены начнут дублироваться.
- **Миграции применяются автоматически при запуске**, в отдельном
  одноразовом контейнере `migrate`. Это не значит, что они каждый раз
  выполняются заново: `alembic upgrade head` видит, что база уже на
  последней версии, и ничего не делает. Миграция реально выполняется один
  раз, когда в коде появилась новая. Если `app` упадёт и перезапустится,
  `migrate` заново не запускается.
  - Почему так: проверяющий запускает проект одной командой, и схема базы
    всегда совпадает с кодом. Если миграция упадёт, приложение не
    запустится, и это сразу видно в `docker compose ps`.
  - В продакшене миграции обычно запускают отдельным шагом при выкатке
    (в CI/CD), а не при старте приложения. Тяжёлую миграцию на большой
    таблице нужно запускать под контролем, а удаление колонок делать в
    несколько релизов. Для тестового проекта с одной таблицей это лишнее.
  - Миграции нельзя запускать из контейнера PostgreSQL: там нет ни Python,
    ни нашего кода.
- **Тесты и линтер запускаются в контейнере `app`**, поэтому для проверки
  нужен только Docker. Для этого в образ поставлены и dev-зависимости
  (pytest, ruff), и тесты. Образ из-за этого немного больше, зато не нужен
  отдельный контейнер для тестов.
- Образ собирается в два этапа: в итоговом образе нет Poetry, процесс
  работает не от root, а `.env` в образ не попадает.
- Docker проверяет, что сервисы работают (healthcheck): для `app` — что
  uvicorn принимает соединения на порту 8000, для `worker` — что он отвечает
  на `celery inspect ping`. Отдельного эндпоинта для этого не сделано: его
  нет в ТЗ, а проверки порта достаточно.

### База данных

- Составной индекс `(ticker, timestamp)`. Все запросы ищут по тикеру и
  сортируют или фильтруют по времени. Индекс только по `ticker` был бы
  бесполезен, у него всего два значения. А составной позволяет сразу
  перейти к нужному тикеру и взять строки по порядку времени. Например,
  последняя цена находится без сортировки всей таблицы.
- Время хранится как UNIX timestamp в секундах (`BigInteger`), как просит ТЗ.
- Тикер хранится строкой, а не enum PostgreSQL. Тогда для нового тикера не
  нужна миграция.

### Фильтр по дате

Формулировка ТЗ «цена с фильтром по дате» допускает два прочтения: цены за
конкретный день или цены за период. Выбран вариант, который подходит под
оба: параметры `date_from` и `date_to`.

- Обе границы включительно: `date_from=2026-10-15&date_to=2026-10-15` — это
  цены за весь день 15 октября.
- Даты считаются в UTC.
- Обе даты необязательны: без `date_to` — до текущего момента, без
  `date_from` — с самого начала.
- Внутри день превращается в промежуток `[00:00 этого дня, 00:00 следующего)`.
  Так цена в 23:59:59 попадает в свой день, а цена в 00:00:00 — в следующий.

### Ответы API

- Неизвестный тикер, неверная дата и `date_from` позже `date_to` — это `422`.
  Проверку делают FastAPI и Pydantic.
- `404` возвращает только `/prices/latest`, если цен ещё нет. Для списков
  отсутствие данных — это не ошибка, они возвращают `200` и `[]`.
- Ошибки предметной области (`NotFoundError` и другие) переводятся в
  HTTP-коды в одном месте. Любая неожиданная ошибка даёт `500` без
  внутренних подробностей, а полный traceback пишется в лог.
- Каждый запрос пишется в лог: метод, путь, статус и время ответа.

### Тесты

- Сервисы тестируются на фейковых репозиториях и источниках цен, без базы и
  сети.
- HTTP-клиенты тестируются на настоящем локальном HTTP-сервере
  (`aiohttp.test_utils.TestServer`). Библиотека aioresponses не подошла: она
  несовместима с текущей версией aiohttp 3.14.
- Репозиторий, API с данными и задача целиком проверяются на настоящем
  PostgreSQL, в отдельной базе `prices_test`. Без неё эти тесты
  пропускаются, поэтому `make test-local` работает и без Docker. В Docker
  (`make test`) тестовая база создаётся сама, и выполняются все тесты.

## Локальная разработка

Для проверки проекта этот раздел не нужен. Он для тех, кто хочет менять код
без Docker. Нужны Python 3.12 и [Poetry](https://python-poetry.org/). База и
Redis берутся из Docker (`make up`).

Установить зависимости:

```bash
make install
```

Запустить тесты локально (тесты с базой пропускаются):

```bash
make test-local
```

Исправить и отформатировать код:

```bash
make format
```

Создать миграцию после изменения моделей:

```bash
make migration NAME="add new column"
```

Запустить API локально с автоперезагрузкой. Сначала остановите контейнер
`app`, чтобы освободить порт 8000:

```bash
docker compose stop app
```

```bash
make run-api
```
